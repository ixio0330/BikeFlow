# GCP 데이터 파이프라인 및 비용 운영 전략

> 확인 기준일: 2026-09-10

## 문서 목적

이 문서는 BikeFlow의 웹·API 배포와 백엔드 데이터 파이프라인의 역할을 구분하고, GCP 서비스를 사용하는 이유와 초기 비용 관리 기준을 기록합니다.

README는 프로젝트의 목표와 기능을 소개하는 문서로 유지하며, 구체적인 클라우드 구성과 비용 관련 의사결정은 이 문서에서 관리합니다.

## 결정 사항

BikeFlow는 React 웹과 NestJS API를 하나의 컨테이너 이미지로 만들고 Cloud Run에 배포합니다.

| 영역        | 서비스          | 역할                                       |
| ----------- | --------------- | ------------------------------------------ |
| 웹·API      | Cloud Run       | React 정적 파일 서빙 및 NestJS 조회 API    |
| 데이터 수집 | Cloud Run       | 서울시 공공데이터 API 호출, 검증 및 정규화 |
| 작업 예약   | Cloud Scheduler | 데이터 수집기의 주기적 실행                |
| 이벤트 전달 | Pub/Sub         | 수집, 저장, 분석, 예측 작업의 비동기 분리  |
| 데이터 분석 | BigQuery        | 과거 대여소 스냅샷 저장 및 분석            |
| 조회 API    | Cloud Run       | 현재 상태와 예측 결과를 프런트엔드에 제공  |
| CI/CD       | GitHub Actions  | 테스트 및 배포 자동화                      |

NestJS는 Vite로 빌드된 React 파일과 버전이 지정된 `/api/v1` API를 함께 제공합니다. 브라우저는 같은 출처로 접근하고, 향후 모바일 앱은 API를 직접 호출할 수 있습니다. 데이터 수집과 저장, 분석, 예측 파이프라인도 GCP 내부에서 완결합니다.

## Pub/Sub 도입 목적

Pub/Sub은 브라우저에 실시간 데이터를 직접 전달하기 위한 수단이 아니라, 백엔드 작업을 비동기로 분리하는 이벤트 버스로 사용합니다.

이를 통해 다음을 경험하고 검증할 수 있습니다.

- 수집기와 저장·분석 처리기의 결합도 완화
- 일시적인 소비자 장애 발생 시 메시지 재전달
- 저장, 알림, 예측 등 새로운 소비자의 독립적인 추가
- 처리량과 실패율을 기준으로 한 모니터링
- 이벤트 기반 서버리스 아키텍처 설계

프런트엔드는 인증 정보가 필요한 Pub/Sub에 직접 연결하지 않습니다. 현재 상태와 예측 결과는 별도의 조회 API를 통해 받으며, 필요한 경우 그 API가 폴링 또는 SSE를 제공합니다.

## 메시지 설계 원칙

### 배치 단위 발행

서울시 API의 한 번의 응답을 대여소별 수천 개 메시지로 무조건 분리하지 않습니다. 작은 메시지는 요청당 최소 과금 단위의 영향을 받으므로, 초기에는 전체 스냅샷 또는 적당한 크기의 청크로 묶어 발행합니다.

메시지에는 다음 정보를 포함합니다.

```json
{
  "schemaVersion": 1,
  "snapshotId": "2026-09-10T12:00:00+09:00",
  "observedAt": "2026-09-10T12:00:00+09:00",
  "chunkIndex": 0,
  "chunkCount": 1,
  "stations": []
}
```

### 중복 처리 대비

Pub/Sub의 기본 전달 방식은 at-least-once이므로 같은 메시지가 다시 전달될 수 있습니다. 소비자는 `snapshotId`, `stationId`, `observedAt` 등을 기준으로 중복 저장이나 중복 집계가 발생하지 않도록 멱등하게 구현합니다.

### 실패 처리

- 처리 성공 후에만 메시지를 승인합니다.
- 재시도 횟수를 초과한 메시지는 Dead Letter Topic으로 보냅니다.
- 스키마가 잘못된 메시지는 원인과 메시지 ID를 구조화된 로그로 남깁니다.
- 오래된 스냅샷이 최신 상태를 덮어쓰지 않도록 `observedAt`을 비교합니다.

## 초기 운영 기준

MVP 단계에서는 다음과 같이 보수적으로 시작합니다.

| 항목                    | 초기 설정                             |
| ----------------------- | ------------------------------------- |
| 서울시 API 수집 주기    | 5분                                   |
| Pub/Sub 발행 단위       | 전체 스냅샷 또는 크기가 제한된 청크   |
| Pub/Sub 구독자          | 저장·처리를 담당하는 구독자 1개       |
| Cloud Run 최소 인스턴스 | 0                                     |
| BigQuery 파티션         | `observedAt` 날짜 기준                |
| 원본 데이터 보관 기간   | 30~90일                               |
| 프런트엔드 갱신         | 캐시된 조회 API를 주기적으로 호출     |
| 리전                    | 가능한 한 GCP 자원을 동일 리전에 배치 |

1분 단위 수집은 데이터 변화와 사용자 가치를 측정한 뒤 도입합니다. 수집 주기를 줄이기 전에 서울시 API 호출 제한, Pub/Sub 처리량, 저장 증가량 및 실제 예측 성능 개선 여부를 함께 확인합니다.
